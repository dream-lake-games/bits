# Getting to a better player connection state, closer to skeleton

Before today, i kind of just loosely had connections working. I would put things in the server, see them replicated to clients, but wasn't really structuring the clients in any kind of way to know how to interact with them.

I wanted just a simple thing I could work with so i could move towards actually making the skeleton of the game. I decided to start with this abstraction:

Unnamed and Named players

Once a player is named, it is persistent. Clients can join back again with the same name and "pick up" that state.

Everone else ends up as an "Unnamed" player.

Client state is ALWAYS derived from server state. When clients detect they are disconnected, they show stuff. When clients are unnamed, they are prompted to put in a name. After that, the client is good. Until the connection drops, in which case they'll see it, reconnect, and then either:

- Just automatically pick their name back up (if we can just immediately reconnect with the same peer id)
- Be prompted to put name again (if we end up having to do a new peer id)

# SERVER STATE

What is the loop then? (I believe we need this to happen in a giant change so each system can believe it is atomically doing stuff)

STABLE STATE: No QuestionActive, No BetsActive

- Invariants:
  - BetsActive implies existence of QuestionActive AND that that QuestionActive has guess_seconds_remaining: None
  - RoundCap implies existence of BetsActive AND that that BetsActive has bets_seconds_remaining: None

Can generate questions as much as we want and just pump them out, certainly if there are no questions in the GeneratedState we should generate one

When there is no active question, try to grab a generated one and make it active

Watch for people's guesses, update the question and tick down active time.

When time runs out (OR everyone has submitted), spawn new bets with BetsActive (and correct round)

- NOTE: For these hashmaps, should always be creating all the buckets we could have at the beginning, then filling/associating as appropriate

Watch for people's bets, update the bets and tick down active time (also locking)

When time runs out (OR everyone has locked), spawn RoundCap

Watch for people continue votes, tick down auto_continue time

When time runs out (OR everyone has voted to continue), retire both the question and the bets, despawn the roundcap

# CLIENT STATE

(note that "state" is a bit generous of a term. it is really "derived state". the client cannot manipulate this directly, it is only from reading state controlled by the server can it act. it _can_ (and should) however send inputs which impact the state updates made by the server)

## No QuestionActive: "waiting for question"

## QuestionActive, No BetsActive

If has not submitted:

- If time remaining, manage input box, potentially send guess
- If no time remaining, "Sorry you didn't submit in time :("

If has submitted:

- Show your guess

## QuestionActive, BetsActive, No RoundCap

If has not locked:

- If time remaining, manage bet inputs, potentially send bets
- If not time remaining, "Sorry, time's up!"

If has locked:

- Show bets

## QuestionActive, BetsActive, RoundCap

Show scoreboard, with delta this round.

# HOST STATE

a.k.a visual server state

## No QuestionActive: "waiting for question"

## QuestionActive, No BetsActive

Just show question + who has submitted and who hasn't

Oh also show the time remaining

## QuestionActive, BetsActive, No RoundCap

Show question, with guesses organized in ascending, with 0 on the left. Update the bets placed on each.

Oh also show the time remaining, and who hasn't locked

## QuestionActive, BetsActive, RoundCap

Show question, with guesses organized in ascending, with 0 on left. Show correct answer prominently, with bets on every guess.

Also show the roundcap status (time left till continue, who has voted to continue).
